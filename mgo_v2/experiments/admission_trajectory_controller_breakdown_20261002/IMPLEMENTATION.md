# Diagnostic implementation and execution binding

Plan: `30614bbc065c140060ef31af9bc4f8615ab16ca5`. Prior results: `e61758e`.

All existing controller, admission, eviction, runtime, CUDA executor and normal benchmark files remain unchanged. The separate `controller_diagnostics.py` module is imported only by the diagnostic worker/replay/tests. It constructs instrumented copies of the live validated controller/Hungarian/Coverage functions by wrapping consecutive original statements in `perf_counter_ns` spans. An AST equality assertion verifies that removing the inserted wrappers recovers the original function exactly. Boundaries fail closed if upstream code changes. This avoids maintaining a second policy implementation and has zero instrumentation overhead when the module is not enabled.

Nested spans are exclusive; parent elapsed time subtracts child intervals. `controller_ns` includes timer overhead; `timer_unattributed_ns` closes the accounting identity. Coverage counter bookkeeping has a separate `diagnostic_accounting` span. Serialization, route capture, plan/cache hashing, token-load calculation and trajectory bookkeeping are outside the subcomponent/plan timers, but affect whole-job diagnostic wall time. Those wall times are never publication speedup evidence. No CUDA synchronization is added inside controller sub-timers.

Hungarian preparation includes token-source/base-destination construction; cost build and SciPy assignment have separate spans. Coverage candidates, global-resident synchronization, gate/damage ranking and victim selection are measured separately. Candidate counts, repeated cache list construction, changed coverage layers, resident additions/removals and matrix sizes are retained. Coverage sync counters describe changes since its previous call, not just the current event.

A dedicated worker rejects any world size other than four and any physical visibility other than `0,1,4,5` before importing torch. One worker job loads the model once and runs exactly six detailed cells: B4 Random/Current, B8 Random/Current, B16 Random/Current. Every cell starts from empty logical/physical residency and history. Two short, three-forward on/off smoke checks (one per policy, B4) precede full measurements and require identical full generated tokens, cache/slot state and metrics on all ranks. These are correctness checks, not extra timing cells. CPU tests cover 320 stateful on/off events with substitutions and evictions.

Each full cell has prefill plus 64 decode forwards (65 generated fixed-work tokens), the prior checkpoint and GSM8K-screen prefix, cache .30, gate .20/similarity .65, Coverage W128/k1/lambda2 and seed42. W128 counts global token rows; R4 B4/B8/B16 decode windows span 8/4/2 events per layer. Every rank saves event diagnostics; rank zero saves raw global router arrays in a local trusted pickle stream. Per-event physical dispatcher fetches must equal rank-local miss operations. Physical bytes use the unchanged native direct-slot executor's 9 MiB/expert accounting, not a new CUPTI capture. Existing physical trace audits remain supporting context.

Retrospective reanalysis of 50 existing Random/Current repeats in ten conditions completes before new GPU execution. CPU replay subsequently runs both policies on both source streams at each batch size, five repetitions each (60 total); own-policy replay is the corresponding subset, not duplicate work. Each repetition starts from a fresh controller and RNG; raw demand, weights, origins, probabilities and event order remain fixed. Raw route traces and detailed rank/event logs stay outside Git. Replays are systems counterfactuals, not model-quality trajectories.

Optional new GPU profiles are omitted in this bounded packet. We reuse prior resident-only sensitivity evidence, report its limitations and do not claim additive communication/compute attribution. GPUs 2,3,6,7 are occupied by other experiments; their CPU/memory/system contention can affect diagnostics and will be disclosed.

Replay execution detail: three independent single-process workers use distinct CPU affinities 180/182/184, one per batch size, with BLAS/OpenMP threads set to one. Each worker runs its source/policy/repetition sequence serially; it can overlap later physical diagnostics. Repetition zero additionally hashes and serializes event decisions outside the measured controller spans. Repetitions 1–4 retain identical component spans and operation counters but serialize only timing/count records; final cache/history/plan and admission/eviction totals must match repetition zero. Raw five-repeat ranges expose timing variability. Component medians are descriptive and may be affected by instrumentation, outside-span cache activity and shared-host contention.
