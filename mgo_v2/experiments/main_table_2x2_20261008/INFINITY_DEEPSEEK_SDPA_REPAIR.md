# DeepSeek MoE-Infinity attention repair

The DeepSeek ShareGPT B64/L1024 warmup in `mt2_deepseek_sharegpt_b64_l1024_infinity_r3_v1` failed before any target timing. MoE-Infinity had selected eager attention, and the prefill softmax attempted an additional 16 GiB allocation on GPU 0. The CUDA OOM was outside the expert cache: its immediate cause was the dense attention matrix at the full frozen batch and input length.

The repair initially selected PyTorch SDPA on all 27 DeepSeek attention layers. The B16/L512 rerun showed a material regression: warmup TPOT rose from 1.271 s/token with eager to 2.817 s/token with SDPA, while peak PyTorch allocation fell. Using SDPA on smaller cells would unfairly slow this baseline. The worker therefore keeps eager attention for the three DeepSeek cells that fit and selects SDPA only for B64/L1024, where eager OOMs. Qwen already used SDPA and retains that path. Expert weights, C30 budgets, EAM eviction priorities, disabled speculative admission, request manifests, and three clean target repeats are unchanged.

The report and queue select an attempt only when its attention backend matches the cell's stated policy: eager for B16/L512, B64/L512, and B16/L1024; SDPA for B64/L1024. The pre-repair DeepSeek runs have no backend receipt but are known from their source code to use eager and remain eligible. The slow SDPA B16/L512 diagnostic and the failed eager B64/L1024 attempt remain on disk, excluded from the table. Backend choice is reported with each DeepSeek MoE-Infinity row, so cross-cell latency comparisons are interpreted with this memory-driven backend change in mind.

The first B64/L1024 SDPA retry was stopped during warmup after GPU memory approached capacity. Inspection of the **loaded** Transformers DeepSeek implementation confirmed that it dispatches through `ALL_ATTENTION_FUNCTIONS` on each forward call, and `sdpa` is registered there; changing the config does select SDPA. A separate checkpoint source file has an older eager-only implementation and is not the runtime implementation. The cause of the new memory spike remains under investigation. A full-input, two-token diagnostic now records memory at every attention layer, while a supervisor headroom guard stops a job before owner GPU free memory falls below the specified threshold. No B64/L1024 Infinity primary result is accepted until a complete three-repeat run passes.
